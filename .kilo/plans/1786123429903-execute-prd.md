# Codeseeker — AI Code Review Bot (Elixir) — Implementation Plan

> Executes PRD.md (v0.1, 8 Aug 2026) end-to-end in ONE continuous pass covering Fase 0-5. First functional milestone is V1+V1.5: `webhook → diff → LLM → inline CRITICAL/HIGH comments + summary comment`, deployed and e2e-verified on a pilot repo. Later tasks in the same pass: skills registry + language skills (as README-style markdown), per-repo toggles + `/codeseeker` commands, guidelines context, exclusions & limits, observability, static-analysis backlog design, deployment.
>
> **Architecture note (per owner decision): NO database.** The bot is fully in-memory. There is no PostgreSQL, Ecto, or Oban. Concurrency is handled by BEAM/OTP (`Task.Supervisor` + `Task.async_stream`), de-duplication by an ETS-backed guard, and the audit trail lives in structured logs. Skills are README-style Markdown files that the bot reads and follows.

## 2. Decisions & Resolved Open Questions

| Question | Decision | Reason |
|---|---|---|
| Project/app name | OTP app `:codeseeker`, module prefix `Codeseeker.*` | Repo folder `codeseeker-service`. Mechanical rename later if a final name is chosen. |
| Storage | **None (in-memory only).** No DB, Ecto, Oban, or Postgres. | Owner decision. Audit trail = structured logs; dedup = in-memory ETS with TTL; stats = in-memory counters. |
| Job model | No queue library. A `DynamicSupervisor` spawns one `Codeseeker.Coordinator` GenServer per PR; files are reviewed with `Task.async_stream(files, max_concurrency: 10)`. | BEAM concurrency is sufficient; no DB means Oban (which needs Postgres) is out. |
| Retry / fault tolerance | In-process bounded retry loop (transient LLM/GitHub errors) with exponential backoff; per-file failure does not abort the PR. | No persistent retry queue; accept that retries do not survive a restart (documented limitation). |
| Idempotency / dedup | `Codeseeker.Dedup` (ETS-backed GenServer) keyed by `(owner, name, pr_number, head_sha)` with `:processing`/`:done` states and a TTL (~1h). | Replaces the DB unique constraint that previously prevented duplicate reviews on webhook redelivery. |
| Skills | README-style Markdown files in `skills/` (e.g. `skills/typescript.md`). Each file is a self-contained instruction doc the bot reads and follows. Extension → skill mapping lives in code config. | Owner decision: "skill set is just like a README, the bot follows it." No Elixir behaviour modules, no DB toggles. |
| Per-repo config | Optional static `config/repos.exs` (loaded at boot) + runtime `/codeseeker` commands. No DB. | Toggles are in-memory/by config file; lost on restart unless set in `config/repos.exs`. |
| Skill priority | `generic` (fallback, always) → `typescript` → `go` → `php` → `elixir` (all five built in this pass). | User input: office repos are mostly TypeScript/JS. |
| Line numbering | LLM reports NEW-file line numbers (right side). Inline only if the line falls inside a right-side hunk range; otherwise demote to summary. | GitHub REST review `comments[].line` refers to the right side; left side is deprecated. |
| Local webhook testing | Tailscale Funnel (`https://<machine>.<tailnet>.ts.net/webhook/github`) → localhost; switch to VPS after deploy. Fallback: smee.io. | Tailscale is already installed (verified). |
| GitHub auth | GitHub App + RS256 JWT (via `joken`) → installation access token cached in a GenServer (1h expiry, refresh-on-401). | PRD §9; least-privilege, not a PAT. |
| Guidelines context | Fetch `docs/engineering-guidelines.md` (raw, default branch) once per PR, truncate ~8KB, append to prompt. | Fase 3 PRD; no per-file fetch (wasteful). |
| Static analysis | Backlog design task at the end: skeleton only, needs a working-tree checkout (outside diff-only architecture). | Separate concern from the diff-only pipeline. |
| Language of plan/prompts/comments | English (plan); prompts & bot comments in English. | Owner decision ("change [the plan] to English"). |

## 3. Prerequisites (User/Ops — do first, in parallel with M0)

1. **Install toolchain** (implementer): `brew install elixir` (>= 1.18, bundles Erlang/OTP 27), then `mix local.hex --force` and `mix archive.install hex phx_new --force`.
2. **Create the GitHub App** at https://github.com/settings/apps/new (user):
   - Name: `Codeseeker` (or final name).
   - Permissions: `pull_requests: write` (post reviews & comments), `contents: read` (diff & guidelines), `metadata: read` (required, automatic).
   - Webhook events: `pull_request` (reviews), `issue_comment` (for `/codeseeker` commands).
   - Webhook URL (temporary): Tailscale funnel URL (see §16); switch to the VPS after deploy.
   - Webhook secret: `openssl rand -hex 32` → `GITHUB_WEBHOOK_SECRET`.
   - Generate a private key PEM, store it safely → `GITHUB_APP_PRIVATE_KEY_PATH`. Record numeric `GITHUB_APP_ID`.
3. **Install the App on the pilot repo** (user): App page → Install → select org + pilot repo (TypeScript/JS repo). Record `installation_id` (from the install page URL or a webhook payload).
4. **Get `DEEPSEEK_API_KEY`** (user) from DeepSeek.

> Note: up to M4 everything works fully against Mox mocks — no real credentials needed. Credentials are only required for real e2e (M11).

### 5.3 Per-repo config (no DB)

  # owner/name => overrides. Omitting a repo means: bot enabled, all manifest skills active,

## 6. Skills System (README-style Markdown Skills)

### 6.1 Concept

A **skill is a Markdown file** in `skills/` — a self-contained instruction document (like a README) that the bot reads and tells the LLM to follow. There are no Elixir behaviour modules and no DB toggles. Adding/editing a skill = editing a Markdown file (and optionally the extension manifest). The file's content is loaded once at boot by `Codeseeker.Skills.Cache` and reused to build prompts.

### 6.2 Skill Markdown format (what the bot follows)

Each file has a consistent shape so the parser can extract optional severity guidance:

```markdown
# Skill: TypeScript

You are a senior TypeScript/JavaScript code reviewer. Focus on promise & async handling,
XSS and DOM security, excessive `any`, race conditions on shared state, and resource leaks
(intervals, listeners).

## Rules
- Check for promises that are not awaited / unhandled rejections.
- Check innerHTML / dangerouslySetInnerHTML / eval used with user input (XSS).
- Check `any` / `as any` that hides real type bugs (report only when it removes safety).
- Check setInterval / event listeners / addEventListener added without cleanup.
- Check errors caught and silently swallowed (no log or recovery).
- Check SQL / DB queries built by string concatenation (injection).

## Severity
- unhandled promise rejection: CRITICAL
- xss: CRITICAL
- sql injection: CRITICAL
- swallowed error: HIGH
- leaked listener: MEDIUM
- excessive any: LOW
```

The `## Severity` section is optional and parsed as `key: SEVERITY` pairs into `%Skill{severity_bias: %{...}}`. All other content is passed verbatim to the LLM as instructions.

### 6.3 Definitions

- `Codeseeker.Skills.Skill` — plain struct `%Skill{name, path, content, severity_bias}`. `load(path)` reads + parses the file; `from_manifest/1` builds it.
- `Codeseeker.Skills.Cache` — GenServer started at boot: scans `skills_dir`, builds `%{name => %Skill{}}`; safe to read concurrently. `get(name)`, `all_names/0`.
- `Codeseeker.Skills.Registry`:
  - `resolve(extension) :: %Skill{}` — `manifest[extension]` → `Cache.get(name)`; if the extension is unknown or the skill file is missing → `Cache.get(fallback_skill)` (`"generic"`).
  - `prompt_for(skill, file_payload, guidelines) :: String.t()` — compose `base_prompt` (§8) + skill content + optional guidelines + diff section.
  - `apply_bias(issues, %Skill{}) :: [%Review.Issue{}]` — raise severity per `severity_bias` when the issue `category`/message matches a key (simple substring match on lowercase message; documented limitation).

### 6.4 Built-in skills (full content summaries; full text lives in the files)

| File | Extensions | Focus |
|---|---|---|
| `generic.md` | (fallback) | Cross-language: obvious bugs, null/undefined access, dropped error handling, duplication, naming, dead code, basic input-validation security. |
| `typescript.md` | `.ts .tsx .js .jsx .mjs .cjs` | Promise/async handling, XSS, excessive `any`, shared-state races, resource leaks. |
| `go.md` | `.go` | Explicit error handling, goroutine leaks, races, context propagation, idiomatic Go, resource `Close`. |
| `php.md` | `.php` | SQL injection, type juggling (`==` vs `===`), XSS, N+1, unsafe `include`/`require`. |
| `elixir.md` | `.ex .exs` | Non-exhaustive matches, unsuperviseed processes, unsafe Ecto `fragment`, mass assignment, un-awaited `Task.async`. |

**Adding a skill** requires no pipeline changes: add `skills/<name>.md`, add its extensions to `:skills_manifest`, and restart the app (or call `Skills.Cache.reload/0`).

## 7. GitHub Integration (App, JWT, Client)

### 7.1 Auth flow (PRD §9: App + JWT, not a PAT)

```
GitHub App private key (PEM) + GITHUB_APP_ID
        │
        ▼
RS256 JWT (joken): claims iss=app_id, iat=now, exp=now+9m
        │
        ▼
POST /app/installations/{installation_id}/access_tokens
   Authorization: Bearer <jwt>
        │
        ▼
installation access token (TTL 1h) → cached in a GenServer
```

**`Codeseeker.Github.AppAuth`** (GenServer, under the Application supervisor):
- State: `%{token: binary, expires_at: DateTime.t()}`.
- API: `token(installation_id) :: {:ok, token} | {:error, %GithubError{}}`.
- Logic: if a cached token exists and has > 30s remaining → return it; otherwise request a new one, cache it, return.
- JWT signing: `Joken.Signer.create("RS256", %{"pem" => pem})`, `Joken.token() |> Joken.with_claims(...) |> Joken.with_signer(...) |> Joken.sign()`.
- Read the PEM in `init/1` from `GITHUB_APP_PRIVATE_KEY_PATH`; crash with a clear message if the file is missing (fail fast).

### 7.2 `Codeseeker.Github.Client` behaviour

```elixir
@type pr_file :: %{path: String.t(), patch: String.t() | nil, additions: pos_integer(),
                    deletions: pos_integer(), status: String.t(), sha: String.t()}
@type review_comment :: %{path: String.t(), line: pos_integer(), side: String.t(), body: String.t()}
@callback list_pr_files(repo :: map(), pr_number :: pos_integer()) ::
            {:ok, [pr_file]} | {:error, %GithubError{}}
@callback post_review(repo :: map(), pr_number :: pos_integer(), head_sha :: String.t(),
                      body :: String.t(), comments :: [review_comment]) ::
            {:ok, map} | {:error, %GithubError{}}
@callback get_raw_contents(repo :: map(), path :: String.t(), ref :: String.t()) ::
            {:ok, binary} | {:error, %GithubError{} | :not_found}
@callback post_issue_comment(repo :: map(), pr_number :: pos_integer(), body :: String.t()) ::
            {:ok, map} | {:error, %GithubError{}}
```

**`Codeseeker.Github.Client.Github`** (Req impl):
- All requests: `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`, `Authorization: Bearer <installation_token>`.
- `list_pr_files/2`: `GET /repos/{owner}/{name}/pulls/{n}/files?per_page=100&page=k`, loop until an empty page or the Link header ends (max 30 pages). Returns `[{path, patch, additions, deletions, status, sha}]`.
- `post_review/5`: `POST /repos/{owner}/{name}/pulls/{n}/reviews` body `{"body": body, "event": "COMMENT", "comments": [{"path": p, "line": l, "side": "RIGHT", "body": b}], "commit_id": head_sha}`. A 422 whose message indicates invalid lines → error with `reason: :invalid_line` (used for the demote fallback in §11).
- `get_raw_contents/3`: `GET /repos/{owner}/{name}/contents/{path}?ref={ref}` with `Accept: application/vnd.github.raw`; 404 → `{:error, :not_found}` (guideline file absent).
- `post_issue_comment/3`: `POST /repos/{owner}/{name}/issues/{pr_number}/comments` (for command replies).
- **Error handling**: all non-2xx → `%GithubError{status, body, reason, retryable?}`; `retryable?` true for 401 (→ force token refresh once and retry once), 403 rate limit → treated as retryable, 5xx. 422 → `reason: :invalid_line`.
- GitHub rate limit (5000/h per installation): mitigated by the in-memory dedup guard (no re-fetch for the same SHA while held) and by not re-running a completed PR within the TTL.

### 7.3 Mox

`Mox.defmock(Codeseeker.Github.Client.Mock, for: Codeseeker.Github.Client)` in `test/test_helper.exs`; jobs/coordinator receive the client module via config/args with the production impl as default.

## 8. Prompt & LLM Contract (DeepSeek)

### 8.1 `Codeseeker.Llm.Prompt` — final prompt composition

```
prompt_final =
  base_prompt()                       # §8.2, always present
  <> "\n\n## SKILL: " <> skill.name <> "\n" <> skill.content
  <> (if guidelines: ) "\n\n## TEAM GUIDELINES (from docs/engineering-guidelines.md):\n" <> guidelines
  <> "\n\n## FILE: " <> path
  <> "\n## DIFF (new-side line numbers already derived from hunks `@@ -a,b +c,d @@`):\n```diff\n" <> patch <> "\n```"
```

Limits: `guidelines` truncated to 8KB by the coordinator; `patch` is bounded by the exclusions logic (§13).

### 8.2 `base_prompt/0` — full text (English, per PRD §6)

```
You are a senior code reviewer. Analyze the file diff below and find CLEAR issues:
bugs, security, performance, or style that violates the rules.
OUTPUT RULES:
1. Output ONLY JSON, no markdown fences, no text outside the JSON.
2. Exact shape: {"issues": [{"line": 12, "severity": "CRITICAL", "category": "security", "message": "...", "recommendation": "..."}]}
3. severity is one of: CRITICAL, HIGH, MEDIUM, LOW, INFO.
4. category is one of: security, perf, bug, style, arch.
5. "line" is the line number in the NEW file (right side of the diff). Use null if unknown.
6. If there are no issues: {"issues": []}
7. Only report NEW changes; do not report context/deleted lines that are not part of the change.
8. Do not repeat the same issue.
9. Avoid false positives: when in doubt, do not report. Prefer zero issues over wrong ones.
10. Write message and recommendation in clear English.
```

### 8.3 `Codeseeker.Llm.DeepSeek` (behaviour + Req impl)

- `chat(prompt) :: {:ok, %{content: String.t(), raw: map}} | {:error, %{type: :timeout | :rate_limited | :api_error, message}}`
- Request: `POST {DEEPSEEK_API_URL}/chat/completions`
  ```json
  {"model": "deepseek-chat",
   "messages": [{"role": "system", "content": "<prompt_final>"}],
   "temperature": 0.1, "max_tokens": 4096,
   "response_format": {"type": "json_object"}}
  ```
- Headers: `Authorization: Bearer <key>`, `Content-Type: application/json`. Timeout 120s (Req `receive_timeout`), connect 10s.
- Error mapping: 429 → `:rate_limited`; 5xx → `:api_error`; timeout → `:timeout`. All three are retryable in the coordinator's in-process retry loop (§10.4).
- **DeepSeek note**: `json_object` mode requires the word "json" in the prompt — satisfied by `base_prompt` (§8.2).

### 8.4 `Codeseeker.Llm.Parser` — parse & validate

1. `content = response.choices[0].message.content` → strip whitespace.
2. `Jason.decode(content)`; on failure → one repair round-trip to DeepSeek with a message like `"Your output was not valid JSON: <content>. Repeat with ONLY JSON."`; if it still fails → `{:error, :unparseable}` (file marked failed, logged, review continues).
3. Map `%{"issues" => [...]}`; each item → `%Review.Issue{file_path: <from job>, line: item["line"], severity: upcase(item["severity"]), category: downcase(item["category"]), message, recommendation, skill: <skill name>}`.
4. Validate the `severity`/`category` enums; drop invalid items + log a warning (never fail the whole file).
5. `apply_bias(issues, skill)` (§6.3) — raise severity per the skill's severity guidance when the category/keyword matches.
6. Output: `{:ok, [%Issue{}]}` (may be empty = `{"issues": []}`).

## 9. Webhook Ingress (Verification, Filtering, Payload)

### 9.1 Routing & plug

`lib/codeseeker_web/router.ex`:
```elixir
scope "/webhook", CodeseekerWeb do
  post("/github", WebhookController, :github)
end
scope "/" do
  get("/healthz", HealthController, :index)   # simple 200, no DB check
end
```

**`CodeseekerWeb.Plugs.RawBodyReader`**: a Plug parser `body_reader` — `{CodeseekerWeb.Plugs.RawBodyReader, :read_body}` that stores the raw body in `conn.assigns[:raw_body]` then calls the normal `Plug.Conn.read_body/2`. Mounted in `endpoint.ex` on `Plug.Parsers` (standard Phoenix pattern for signature verification). No JSON parsing happens before verification — only raw bytes.

### 9.2 `WebhookController#github` — sequential algorithm

1. **Get raw body**: `conn.assigns[:raw_body]`. Empty → 400.
2. **Verify signature** (mandatory, PRD §4):
   - `sig_header = get_req_header(conn, "x-hub-signature-256")` → format `"sha256=<hex>"`.
   - `expected = "sha256=" <> Base.encode16(:crypto.mac(:hmac, :sha256, secret, raw), case: :lower)`.
   - `Plug.Crypto.secure_compare(sig_header, expected)` (timing-safe). Fail or missing → `conn |> put_status(401) |> json(%{error: "invalid signature"})` + warning log (possible attack).
3. **Filter event**: `event = get_req_header(conn, "x-github-event")`:
   - `"pull_request"` → proceed to step 4.
   - `"issue_comment"` → action `"created"` and `payload.comment.body` starts with `/codeseeker` → dispatch command (see §12) → 200.
   - anything else → `json(%{ok: true})` (200 no-op; GitHub needs a fast ack).
4. **Filter pull_request action**: `payload["action"] in ["opened", "synchronize"]`; otherwise → 200 no-op (e.g. `closed`, `labeled`).
5. **Dispatch** (`Codeseeker.CoordinatorSup.start_child/1`):
   - args: `%{repo: %{owner: repository.owner.login, name: repository.name, github_repo_id: repository.id, installation_id: installation.id}, pr_number: payload["number"], head_sha: payload["pull_request"]["head"]["sha"], base_sha: payload["pull_request"]["base"]["sha"]}`.
   - Respond `json(%{ok: true, dispatched: "coordinator"})` BEFORE the coordinator finishes (fast ack < 1s).
6. **Error handling**: malformed payload (no `repository`/`pull_request`) → 400 + log; invalid signature → 401 (step 2); unexpected exception → 500 + log (the endpoint stays safe — wrap in `try/rescue`).

### 9.3 Security (PRD §8)

- Mandatory HMAC-SHA256 signature; timing-safe compare; secret from env.
- Do not trust the sender IP (GitHub IP-range verification optional — not in V1; note in README).
- Never log full payloads (may contain data); log only `repo`, `pr_number`, `event`, `action`.
- Respond fast; all heavy work happens asynchronously.

## 10. In-Memory Pipeline (No DB): Coordinator, Dedup, Concurrency, Retry

### 10.1 High-level flow

```
GitHub webhook (pull_request opened/synchronize)
        │  (verified, HMAC-SHA256)
        ▼
WebhookController → CoordinatorSup.start_child(pr)
        │
        ▼  Codeseeker.Coordinator (GenServer, one per PR)
        ├── Dedup.begin_processing(key) → :duplicate? bail out
        ├── list_pr_files (paginated)
        ├── Exclusions.filter → kept ++ skipped
        ├── fetch guidelines (optional)
        ├── Task.async_stream(kept, &review_file/1, max_concurrency: 10)  → per-file issues
        │        └──  resolve skill → build prompt → DeepSeek (retry loop) → parse
        ├── Review.aggregate(issues, skipped, warnings) → inline ++ summary
        ├── post_review (with 422 invalid-line fallback)
        ├── Dedup.mark_done(key)
        └── Stats.record(...) + structured log
```

### 10.2 `Codeseeker.CoordinatorSup` (DynamicSupervisor)

- Started under the Application supervisor.
- `start_child(pr_args)` → starts a `Codeseeker.Coordinator` GenServer for the given PR. Multiple PRs run concurrently; concurrency within a PR is bounded by `Task.async_stream`'s `max_concurrency` (10).

### 10.3 `Codeseeker.Coordinator` (GenServer per PR)

State: `%{pr: pr_args, phase: :running}`. `perform` runs in `handle_continue` (not in `init`, so the webhook returns fast).

Steps:
1. **Dedup guard**: `Dedup.begin_processing(key)` where `key = {owner, name, pr_number, head_sha}`. If it returns `:duplicate` → log and stop (redelivery or concurrent duplicate).
2. **Fetch files**: `Github.Client.list_pr_files(repo, pr_number)` (pagination automatic). On a retryable error → retry loop (§10.4); on final failure → log error, `Dedup.mark_done`, stop.
3. **Filter & limit** (§13): `{kept, skipped, warnings} = Exclusions.filter(files)`. If `kept == []` → log "nothing to review", `Dedup.mark_done`, stop (no review posted).
4. **Guidelines**: `Github.Client.get_raw_contents(repo, guidelines_path, base_sha)` → success → truncate 8KB; `:not_found` → nil; error → warning.
5. **Review files**: collect issues via
   ```elixir
   results =
     kept
     |> Task.async_stream(&review_file(&1, repo, guidelines), max_concurrency: review_concurrency, timeout: 150_000, on_timeout: :kill_task)
     |> Enum.to_list()
   ```
   Each `review_file/3` returns `{:ok, [%Issue{}]}` or `{:error, reason}`. Errors are logged and counted; the PR continues.
6. **Aggregate**: `Review.aggregate(issues, skipped, warnings, pr)` (§11) → `%{inline: [comments], summary_body: body, demoted: [...]}`.
7. **Post**: `Github.Client.post_review(repo, pr_number, head_sha, summary_body, inline)`. On `{:error, %{reason: :invalid_line}}` → demote all inline to summary and post again without comments (see §11.4). On success → log result.
8. **Finish**: `Dedup.mark_done(key)`, `Stats.record(...)`, `Logger.info(review_summary)`.

### 10.4 In-process retry (replaces Oban retries)

`Codeseeker.Coordinator.retry(fun, max_retries, backoff_ms)`:
- Runs `fun`; on a retryable result (`:timeout`, `:rate_limited`, `:api_error`, GitHub 401/403/5xx) sleeps `backoff_ms[i]` and retries, up to `max_retries` (3 for LLM, config `:llm.max_retries`).
- After the last attempt fails → returns the final error; the caller logs it and keeps going (per-file/per-PR best-effort).
- Used for: DeepSeek calls, GitHub file-list fetch, GitHub review post.
- **Limitation (explicit)**: retries do not survive an application restart, because there is no persistent queue. A webhook redelivery after restart would re-run the PR (dedup TTL also lost). Documented in README.

### 10.5 `Codeseeker.Dedup` (ETS-backed GenServer)

- ETS table `:codeseeker_dedup` (public, `:set`), owned by a GenServer.
- Key: `{owner, name, pr_number, head_sha}`. Value: `{:processing | :done, inserted_at}`.
- `begin_processing(key)`:
  - no entry → insert `:processing`, return `:ok`.
  - existing `:processing` → `:duplicate` (already running).
  - existing `:done` and age < TTL → `:duplicate` (already reviewed recently).
  - existing `:done` and age >= TTL → overwrite `:processing`, return `:ok`.
- `mark_done(key)` → set `:done`.
- Periodic cleanup (GenServer `handle_info` timer, e.g. every 5 min) evicts entries older than `dedup_ttl_seconds` (default 3600).

### 10.6 Concurrency & rate limiting

- Per-PR: `Task.async_stream(..., max_concurrency: 10)` bounds DeepSeek burst.
- Global: `Codeseeker.CoordinatorSup` starts one coordinator per PR; if many PRs arrive at once, total LLM concurrency = `#PRs × 10`. To avoid bursts, add a simple global in-process semaphore (an `Agent`/ETS counter gating DeepSeek calls) if `:rate_limited` appears in logs — documented as a tuning knob, not built by default.

## 11. Aggregator & Review Posting (Algorithms, Template, API Payload)

### 11.1 `Codeseeker.Review` (pure module, easy to test)

`aggregate(issues, skipped, warnings, pr) :: %{inline: [review_comment], summary_body: String.t(), demoted: [%Review.Issue{}]}`

Algorithm:
1. `min_inline = PerRepo.min_inline_severity(repo)` (default `"HIGH"`); `inline_candidates = issues with severity >= min_inline` (ordered CRITICAL > HIGH > MEDIUM > LOW > INFO).
2. **Line validation** per file (via `Codeseeker.Hunk`):
   - `Codeseeker.Hunk.new_line_ranges(patch) :: [{start, finish}]` — parse each `@@ -a,b +c,d @@` → new-side range `[c, c+d-1]` (for d > 0).
   - A line is valid ⇔ `line != nil` and `line ∈ one of the ranges` (approximation — a line could be context/deleted within a range; GitHub may 422, handled by the fallback in §11.4).
   - Invalid → `demoted` (goes into the summary with a label).
3. **Render summary markdown** (`summary_body`):
   ```markdown
   ## 🤖 Codeseeker Review — PR #{pr_number}
   Automatic review (skills: typescript, generic) on `#{head_sha[0..7]}`.

   ### #{file_path} — N issues (M inline, K summary)
   - **[SEVERITY] [category]** message
     - Suggestion: recommendation
   ### Notes
   - Skipped files: package-lock.json (lockfile), dist/bundle.min.js (generated)
   - Diff too large: src/big.ts (> 1500 lines) → manual review recommended
   - N files failed to review (LLM/network)
   ```
   Rules: inline issues are not repeated in the summary (only counted in the section header); `demoted` issues appear with an `[inline failed]` marker; the `Notes` section appears only if it has content.
4. Return the struct.

### 11.2 Example `post_review` payload

```json
{
  "commit_id": "a1b2c3d4e5f6...",
  "event": "COMMENT",
  "body": "## 🤖 Codeseeker Review — PR #12\n...",
  "comments": [
    {"path": "src/api.ts", "line": 84, "side": "RIGHT",
     "body": "**[CRITICAL] [security]** Query string built by concatenating user input.\n\n**Suggestion:** Use a parameterized query / prepared statement."}
  ]
}
```

### 11.3 Inline vs summary (PRD §2.4, §4 step 8)

| Severity | Handling |
|---|---|
| CRITICAL, HIGH | Inline comment (when the line is valid) |
| MEDIUM, LOW, INFO | Summary only |

`repo.min_inline_severity` can raise the threshold (e.g. `"CRITICAL"` only) when false positives are high (Fase 4 tuning, PRD §8).

### 11.4 422 `invalid_line` fallback

- If `post_review` returns `{:error, %{reason: :invalid_line}}`: re-render the summary body to include the previously-inline issues with an `[inline failed — invalid line]` marker, then `post_review` again with `comments: []`.
- If the second post also fails with 422 → log the error and record the review as failed (no review posted).

## 12. Per-Repo Config & `/codeseeker` Commands

### 12.1 `Codeseeker.PerRepo` (in-memory config)

- Backed by an `Agent`/ETS initialized from `config :codeseeker, :repos` at boot (§5.3).
- API: `enabled?(repo)`, `skills(repo) :: [name]`, `min_inline_severity(repo)`, `effective_skills(repo, extensions)` (intersection of manifest skill for each extension with the repo's enabled skills; `generic` always allowed).
- `/codeseeker` commands mutate this state at runtime. Restart re-reads `config/repos.exs`; runtime-only changes are lost (documented).

### 12.2 `/codeseeker` commands (triggered by `issue_comment` webhook, action `created`)

- Pattern: `^/codeseeker\s+(enable-skill|disable-skill|status)(\s+(\w+))?\s*$` on `payload.comment.body`.
- Dispatch (in `WebhookController`, or a small `Codeseeker.Commands` module invoked inline — no queue needed for a fast operation):
  1. Upsert the repo context (confirm the bot is installed — webhooks only fire for installed repos).
  2. `enable-skill|disable-skill <name>`: validate `<name>` exists in `Skills.Cache.all_names()` → `PerRepo.enable/disable_skill` → reply via `post_issue_comment` (mention `@user`: "Skill `go` enabled for this repo.").
  3. `status`: reply with the repo's enabled skills, bot `enabled?`, and `min_inline_severity`.
  4. Unknown skill → reply with the list of available skills.
- **Permission**: V1 — anyone who can comment on a PR can trigger (internal single-org tool; PRD §2 Non-Goals: not multi-tenant). Note as a known limitation in README; membership verification via the `members: read` API is backlog.

## 13. Exclusions & Size Limits (`Codeseeker.Exclusions`)

`filter(files) :: {kept, skipped_paths, warnings}` — evaluate per file, in order:

1. **Forbidden extension/pattern** (regex from `:exclusions.patterns`, §5.2): lockfiles (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `go.sum`, `mix.lock`, `*.lock`), generated/minified (`*.min.js`, `*.min.css`, `*.pb.go`, `dist/`, `build/`, `vendor/`, `node_modules/`), binary assets (`*.svg`, `*.png`, `*.jpg`, `*.ico`) → skip + record in `skipped_files` (reason "excluded pattern").
2. **Binary detection**: `patch` contains `"Binary files differ"` or a NUL byte → skip + warning "binary file".
3. **Size limit**: `String.length(patch) > 300_000` OR `additions > 1_500` → skip + warning `"diff too large (>N lines/bytes) — manual review recommended"` (PRD §8).
4. **`patch == nil`** (API sent no patch, e.g. a pure rename) → skip + warning "no patch".
5. Everything else → `kept`.

Maximum files reviewed per PR: **30** (`:max_files_per_pr`). If more, take the first 30 + warning "N files not reviewed (30-file limit)".

## 18. Failure Modes & Mitigations

| # | Scenario | Impact | Detection | Mitigation (implementation) |
|---|---|---|---|---|
| 1 | Webhook redelivery / duplicate event | Duplicate review | dedup key `(repo,pr,sha)` | `Dedup` `:processing`/`:done` + TTL; e2e redelivery test |
| 2 | Bad signature / brute force | Attack | warning log on 401 | timing-safe compare; never log body |
| 3 | GitHub token expires mid-run | 401 on calls | `%GithubError{status: 401}` | refresh + retry once, then retry loop |
| 4 | GitHub rate limit 403 | Fetch/post fail | 403 retryable | retry with backoff; dedup prevents re-fetch for the same SHA |
| 5 | DeepSeek timeout / 429 / 5xx | File not reviewed | error type in logs | in-process retry loop; `max_concurrency`; per-file failure does not abort the PR |
| 6 | LLM output not JSON | File without review | `:unparseable` | repair retry once; then skip + log |
| 7 | Wrong line number / outside hunk | GitHub 422 | 422 response | local hunk validation (demote) + 422 fallback (post without comments) |
| 8 | Very large diff / many files | Rate limit / cost | counters | Exclusions §13: skip + "manual review" warning |
| 9 | Repo disabled / bot uninstalled | No-op work | webhooks stop | `PerRepo.enabled?` → skip |
| 10 | App restart mid-review | In-flight PR lost | — | no persistent queue; documented limitation; webhook redelivery re-runs (dedup TTL also lost) |
| 11 | Webhook secret leak/rotation | — | — | change env + restart; PRD §8 rotate periodically |
| 12 | Concurrent identical PRs | Duplicate review | dedup `:processing` | only one coordinator runs, others `:discard` |
| 13 | False positives high → team ignores bot | Adoption failure (PRD §8) | 2-weekly eval | raise `min_inline_severity`; strict bias in `base_prompt` (rules 8-9) |

- Cross-file context-aware review (V2 PRD): only per-file diff + guidelines for now.

- Caching GitHub `GET files` per SHA in a store (PRD §8) — dedup guard already prevents the main re-fetch; explicit caching is backlog if rate limits become an issue.
